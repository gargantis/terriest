M4 extends it with the frame-time run, the device runs and the manual checks (PLAN §17).

- **Pending lines:** a line whose device run hasn't happened stays marked pending here. So does a browser L236 names that hasn't been run, such as Firefox or Edge on the phone (Q-13).

## Frame-time criteria (L286)

Copied from roslambo's, as L286 asks: the pass figures and the 60 Hz rule. The run they judge, the bench's scripted 4-a-side match, is set out in PLAN §16 and written in here at M4.

- **Pass:** the interval between animation frames has p95 ≤ 18 ms and max ≤ 50 ms.
- **The display at 60 Hz:** a faster display would hide dropped frames inside the criteria.
  - On the Pixel 8a, Smooth Display runs at up to 120 Hz. Turn it off (Settings → Display → Smooth Display) for the run.
  - On Windows, set the refresh rate to 60 Hz (Settings → System → Display → Advanced display), as for run 6.
- **terriest's own conditions:** frame times are judged on a visible page (D-31). The phone's run is judged at the render quality phones start with, and the run never changes quality (D-33). The gate never judges frame time, because it draws in software (C-6).

### M3's desktop connection, settled provisionally (owner-pending)

**The owner's check** (PLAN §16, M3's design §15): two desktop browsers on Windows, such as Chrome and Firefox, play a match through `npm run dev:local` on the `#test=net` page, one the keeper and one a player, at 1 a side, each terrier driven by the bots' brain (`script=brain`), and each page's status shows them connected, ticking and in agreement to the match's end.

1. In the checkout, in WSL2, run `npm run dev:local`. It prints the local relay's port, then the dev server's address, http://localhost:5173/ unless that port is taken; if it prints another, the addresses below take that one.
2. In the first browser, open the keeper's page, in pack A, and wait until its status shows a timeline. The dev server prepares the page's modules at its first load, and may reload it once.

   `http://localhost:5173/#test=net&room=TERR-1EST-DESK-T0PM-3000-4&k=0&role=keeper&pack=0&packSize=1&minutes=1&script=brain&ready=600`

3. Within a minute, in the second browser, open the player's page, in pack B:

   `http://localhost:5173/#test=net&room=TERR-1EST-DESK-T0PM-3000-4&k=1&role=player&pack=1&script=brain&ready=600`

4. Watch both statuses, which refresh every half second: one peer on each; the local, final and drawn ticks climbing; the same state hash at the same final tick on both, a whole second's tick, so the two can be compared by eye; no disagreement or resync; and, a minute or two later, the same "Ended at tick …" line on both, after overtime's golden goal if the score was level at 0:00.

The room ID is fixed, and only the local relay ever sees it: the pages contact no public relay. Their ICE is the default, as a deployed page's is, so they connect as a deployed match would: each browser also asks `third-party.json`'s two STUN servers for its public address (M3-Q4). To contact nothing outside this machine, add `&ice=none` to both addresses, and neither asks a STUN server. Each page presses Ready once, at tick 600, 10 s into the match, or as soon after as its terrier is in the roster, and a Ready lasts a minute: if the player's page joins more than a minute after the keeper's Ready, the match never starts, so both pages are closed and opened again.

**If neither page shows a peer,** suspect the relay first: no run has yet tested a Windows browser reaching it. It listens on 127.0.0.1 inside WSL2, and the page asks for it at `ws://localhost:<port>`, the port `npm run dev:local` printed first, relying on WSL2's localhost forwarding as the page's own address does. The browser's console then shows that WebSocket failing. That's a fault of `dev:local`'s to report and fix, not a failed check.
